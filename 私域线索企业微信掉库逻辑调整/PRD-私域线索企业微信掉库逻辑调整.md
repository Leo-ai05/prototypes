## 二、需求概述

- **背景/现状**：当私域线索尚未由规则或扣子触发转人工时，现有掉库起算口径无法准确反映人工承接阶段。
- **需求目标**：当上线后首次出现有效转人工时，系统应按企业微信现行掉库规则生成掉库日期，并在私域线索池展示计算结果。
- **核心逻辑简述**：系统忽略销售主动转人工及其他来源，以首次规则触发或扣子触发的转人工作为起算事件；首次有效事件之前不计算、不掉库，之后沿用企业微信掉库机制。

## 三、术语表

| 术语 | 定义 |
|---|---|
| 私域线索 | 已进入私域线索池并按意向等级分层管理的用户线索 |
| 有效转人工 | 由规则触发或扣子触发的转人工；销售主动及其他来源不计入 |
| 首次有效转人工 | 同一条线索上线后第一次发生的有效转人工 |
| 掉库日期 | 以首次有效转人工时间为起点，按当时生效的企业微信掉库规则计算的线索到期时间 |

## 四、调整范围

| 功能模块 | 调整内容 |
|---|---|
| 私域线索掉库计算 | 改为在上线后首次有效转人工发生时开始计算掉库日期 |
| 转人工来源判定 | 仅规则触发、扣子触发可生效，销售主动及其他来源忽略 |
| 重复事件处理 | 首次有效转人工生成结果后，后续转人工与数据重置不重复计算 |
| 私域线索池列表 | 新增“首次转人工时间”“掉库日期”两列，仅展示，不新增筛选和排序 |
| 企业微信掉库联动 | 掉库周期及后续改期沿用现有企业微信掉库机制 |

## 五、业务流程图

**主流程：首次有效转人工触发掉库计算**

```mermaid
flowchart TD
    A[私域线索发生转人工] --> B{是否上线后新事件}
    B -->|否| C[不处理历史事件]
    B -->|是| D{来源是否规则或扣子}
    D -->|否| E[忽略本次事件]
    D -->|是| F{是否已有首次有效时间}
    F -->|是| G[保留原时间与掉库日期]
    F -->|否| H[记录首次有效转人工时间]
    H --> I[按企微规则生成掉库日期]
    I --> J[列表展示两个时间]
    E --> K1[线索继续留库]
    G --> K2[流程结束]
    J --> K3[到期后按现行机制掉库]
```

## 七、功能需求详细描述

### 7.1 首次有效转人工判定

| 功能名称 | 功能说明 | 功能类型 | 是否必填 | 交互说明 | 备注 |
|---|---|---|---|---|---|
| 适用线索判定 | 仅对私域线索执行本次掉库起算逻辑 | 后台规则 | 是 | 转人工事件发生时先确认线索当前属于私域线索 | 非私域线索沿用原有规则 |
| 生效时间判定 | 仅处理需求上线后新发生的转人工事件 | 后台规则 | 是 | 上线前历史已转人工线索不补算、不改写现有结果 | 冒烟数据待产品提供 |
| 有效来源判定 | 规则触发、扣子触发属于有效来源 | 后台规则 | 是 | 销售主动转人工及其他来源不记录首次有效时间，不生成掉库日期 | 有效来源严格限定为两类 |
| 首次事件判定 | 取上线后第一次有效转人工作为起算事件 | 后台规则 | 是 | 若销售主动转人工在先、规则或扣子触发在后，则以后一次作为首次有效转人工 | 销售主动事件不占用首次资格 |

### 7.2 掉库日期计算

| 功能名称 | 功能说明 | 功能类型 | 是否必填 | 交互说明 | 备注 |
|---|---|---|---|---|---|
| 首次转人工时间记录 | 记录首次有效转人工开始时间 | 后台规则 | 是 | 首次有效事件确认后立即记录，后续事件不得覆盖 | 以转人工实际开始时间为准 |
| 掉库日期生成 | 以首次有效转人工时间为起点生成掉库日期 | 后台规则 | 是 | 计算周期沿用事件发生时生效的企业微信掉库规则 | 不在本需求固定掉库天数 |
| 规则改期联动 | 企业微信掉库规则调整时同步处理未掉库线索 | 后台规则 | 是 | 是否改期及改期方式完全沿用现有企业微信处理机制 | 不新增独立改期规则 |
| 到期掉库 | 到达掉库日期后执行线索掉库 | 后台规则 | 是 | 掉库行为、掉库去向和掉库原因沿用现有企业微信掉库机制 | 首次有效事件前不执行掉库 |

### 7.3 重复事件与异常处理

| 场景 | 系统行为 | 可观察结果 |
|---|---|---|
| 同一线索多次收到相同有效事件 | 仅首次成功记录，重复事件不得覆盖 | 首次转人工时间和掉库日期保持不变 |
| 首次有效转人工后再次转人工 | 忽略重新计算请求 | 列表继续展示原时间 |
| 首次有效转人工后执行数据重置 | 数据重置不得改变掉库起算结果 | 列表继续展示原时间 |
| 销售主动转人工后发生规则或扣子转人工 | 忽略销售主动事件，以后续首次有效事件起算 | 两列展示后续有效事件对应结果 |
| 仅发生销售主动或其他来源转人工 | 不记录、不计算、不掉库 | 两列均显示“--” |
| 有效事件信息不完整或计算失败 | 不写入不完整结果，并记录失败以便排查 | 两列保持“--”，线索不得因此提前掉库 |
| 并发收到多个有效事件 | 只允许最早成功确认的一次成为首次有效事件 | 两列只展示一组稳定结果 |
| 列表加载失败 | 沿用现有列表失败处理 | 不单独展示错误时间 |

### 7.4 私域线索池列表

| 字段名称 | 字段说明 | 字段来源 | 展示与交互 | 备注 |
|---|---|---|---|---|
| 首次转人工时间 | 展示上线后首次由规则或扣子触发转人工的开始时间 | 首次有效转人工判定结果 | 位于“企业微信添加时间”之后；仅展示，不可编辑，不提供筛选和排序 | 无有效事件、历史不补算或取值异常时显示“--” |
| 掉库日期 | 展示根据首次有效转人工时间及企业微信规则生成的掉库时间 | 企业微信掉库计算结果 | 位于“首次转人工时间”之后；仅展示，不可编辑，不提供筛选和排序 | 未生成、计算失败或取值异常时显示“--” |

列表其余字段、意向分层页签、统计卡片、搜索、分页、行操作及详情跳转均沿用现有交互。新增两列对当前具备私域线索池查看权限的用户可见，不新增权限。

### 7.5 上线兼容与测试数据

1. 上线前已发生转人工的历史私域线索不回溯、不补算；若上线后再发生首次规则或扣子触发转人工，则按该次事件开始计算。
2. 上线前未转人工且上线后仍未发生有效转人工的线索不计算掉库日期。
3. 需要准备至少五类冒烟数据：从未转人工、仅销售主动转人工、销售主动后规则触发、扣子首次触发、首次有效后再次转人工。
4. 冒烟账号与具体线索数据待产品提供。
